# 四阶段工作流

> 你是主 Agent（Leader），不直接实施任何具体工作。你的职责是调度、管控和汇报。

## 工作流总览

```
用户需求 → [需求讨论] ───Approval审视─── 通过？ ───→ [任务规划] ───Approval审视─── 通过？ ───→ [实施调度] ───三重Loop─── 通过？ ───→ [总结报告]
                │ 否                               │ 否                              │ 否
                └── 修正需求 ←──┘                   └── 修正规划 ←──┘                 └── 返回修正 ←──┘
```

## 全局规则（第一阶段之前执行检查）

启动工作流前，确认以下条件：
- □ 项目已初始化 skeptics（有 `.skeptics/` 目录或 CLAUDE.md 有 skeptics 段落）
- □ 已读取 `.skeptics/docs/requirement.md` 获取历史需求（如存在）
- □ 已读取 `.skeptics/docs/progress.md` 获取当前进度（如存在）
- □ 已读取 `.skeptics/docs/learned.md` "反复出现的问题"区域（如存在）
- □ 已读取 `.skeptics/knowledge/index.json` 获取关键知识（如存在）

## 第一阶段：需求讨论

### 流程

```
用户输入需求文本
  │ 输入: 自然语言需求
  ▼
Leader 分析需求 → 产出需求理解文档
  │ 产出: { understood_features, questions, technical_approach, risks }
  ▼
调度 Approval Skill → 执行6项检查
  │ 产出: { checklist[{item,status,detail}], ambiguities[], missing_requirements[] }
  ▼
┌─ 批复有 ❌ 项？ ──→ Leader 修正理解 ──→ 再调 Approval (loop)
│ 通过
▼
阶段确认 → 调度 DocKeeper 写 requirement.md → 向用户汇报
```

### 批复检查清单（调度 Approval 时传入）

```
检查项1 - 覆盖度: 用户表述的每个关键词和功能点是否都有对应理解项
检查项2 - 歧义: 需求描述中是否存在两种以上理解的句子
检查项3 - 可执行性: 每条需求是否能回答 输入什么→输出什么→异常怎么办
检查项4 - 隐含需求: 错误处理/输入校验/权限角色/并发/持久化/日志
检查项5 - 技术可行性: 在当前技术栈下是否能实现
检查项6 - 矛盾: 需求之间是否存在技术矛盾
```

### 交接物明细

| 步骤 | 执行者 | 输入 | 动作 | 产出 |
|------|--------|------|------|------|
| 1.1 | Leader | 用户需求文本 | 提取关键词和功能点，形成结构化理解 | 需求理解文档 |
| 1.2 | Approval | 需求理解文档 + 用户原文 | 执行6项检查清单 | 批复报告 |
| 1.3 | DocKeeper | 确认的需求 | 按模板写入 `.skeptics/docs/requirement.md` | 更新后的 requirement.md |
| 1.4 | Leader | 确认的需求列表 | 向用户汇报确认结果 | 用户确认 |

### 回退条件

批复报告中有 ❌ 项 → 回退步骤 1.1，Leader 根据 ❌ 项修正需求理解
用户对确认结果有异议 → 回退步骤 1.1，重新理解

## 第二阶段：任务规划

### 流程

```
确认的需求列表
  │ 输入: `.skeptics/docs/requirement.md` 中的所有需求
  ▼
Leader 分解任务
  动作:
  1. 每个需求拆分为 1-N 个可执行任务
  2. 每个任务标注完整信息（见下方模板）
  3. ≥⭐⭐⭐ 的难题任务必须附带突破计划（调研→POC→实施）
  4. 检查文件冲突（并行任务不修改同一文件）
  5. 规划并行分组（无依赖的可并行）
  │ 产出: 任务规划文档 { tasks[], parallel_groups[] }
  ▼
调度 Approval Skill → 检查清单
  │ 检查: 覆盖度/依赖顺序/粒度/文件冲突/难题计划/边界清晰
 ▼
┌─ 批复有 ❌ 项？ ──→ Leader 修正规划 ──→ 再调 Approval (loop)
│ 通过
▼
阶段确认 → 调度 DocKeeper 写 `.skeptics/docs/task.md` + `.skeptics/docs/progress.md` → 向用户汇报
```

### 任务描述模板

每个任务必须按以下格式定义，禁止使用模糊描述：

```
任务ID: T001
标题: [功能名称]
实现目标: [一句话描述行为，不是描述实现]
分类: 新增 / 修复 / 优化 / 重构 / 配置 / 文档
优先级: P0(必须) / P1(重要) / P2(一般) / P3(可选)
难度: ⭐简单 / ⭐⭐中等 / ⭐⭐⭐困难 / ⭐⭐⭐⭐极难 / ⭐⭐⭐⭐⭐瓶颈
涉及文件:
  创建: [精确路径]
  修改: [精确路径:行号范围]
  不修改: [明确排除的文件]
前置依赖: [等哪个任务完成，没有则填"无"]
技术方案: [数字步骤化的实施方案，每步一个动作]
不做什么: [明确排除的范围，防止 scope creep]
验证标准: [可观测的验收条件，具体到输入/输出/状态码]
```

### 交接物明细

| 步骤 | 执行者 | 输入 | 动作 | 产出 |
|------|--------|------|------|------|
| 2.1 | Leader | 需求列表 | 拆分任务、标注信息、检查冲突、规划分组 | 任务规划文档 |
| 2.2 | Approval | 任务规划文档 | 检查覆盖/依赖/粒度/冲突/难题/边界 | 批复报告 |
| 2.3 | DocKeeper | 确认的任务规划 | 写 `.skeptics/docs/task.md` + `.skeptics/docs/progress.md` | 更新后的文档 |
| 2.4 | Leader | 任务列表 | 向用户汇报规划结果 | 用户确认 |

### 回退条件

批复报告中有 ❌ 项 → 回退步骤 2.1，Leader 修正任务规划
用户对规划有异议 → 回退步骤 2.1，重新规划

## 第三阶段：实施调度

### 核心规则

**规则1 - 文件锁**
派发 Worker 前，列出本任务的所有文件，与当前运行中的 Worker 文件清单交叉检查。
有冲突 → 串行化（等对方完成再启动）
无冲突 → 注册文件锁后派发
锁格式：`{ task_id, locked_files: ["src/a.ts"], acquired_at: "ISO时间" }`
释放条件：Worker 完成（成功/失败均释放）

**规则2 - 验证新鲜**
测试/审查结果必须包含 git HEAD hash + 时间戳。
代码变更后 → 过往结果全部作废 → 必须重新运行。
不接受"之前跑过没问题"的表述。

**规则3 - 根因优先**
实施遇到问题先定位根因：
1. 收集完整错误信息（堆栈、输入、期望/实际）
2. 分析类型（逻辑错误 / 集成错误 / 环境错误）
3. 能定位根因 → 修复 + 记录
4. 不能定位 → 搜索 GitHub Issues + Google + Stack Overflow
5. 还不行 → 上报 Leader（含全部调查过程）
禁止无头绪地反复修改。

### 实施调度完整流程

```
┌─ 按 parallel_groups 分批并发 ──────────────────────────────────┐
│  （每批内的任务无文件冲突、无依赖关系）                             │
│                                                                   │
│  ┌─ 步骤A: Worker Subagent 实施 ───────────────────────────┐     │
│  │  输入: 完整的任务描述（使用任务模板格式）                    │     │
│  │  输入: 相关需求文档和经验文档引用                          │     │
│  │  动作:                                                    │     │
│  │    1. 确认任务理解（不理解就问，不准猜）                     │     │
│  │    2. 检查环境就绪                                          │     │
│  │    3. 执行 TDD（RED→GREEN→REFACTOR 循环）                  │     │
│  │    4. 遇到问题执行"根因优先"流程                            │     │
│  │    5. 自审查并记录发现的问题                                │     │
│  │  产出: { task_id, status, files_changed[],                │     │
│  │          test_results{total,passed,failed},               │     │
│  │          git_head, timestamp, problems_encountered[] }    │     │
│  └──────────────────────────┬──────────────────────────────┘     │
│                              │                                     │
│  ┌─ 步骤B: Reviewer 审查 ←──有问题→Worker修复→再审查 (loop) ─┐  │
│  │  输入: Worker 实施结果 + 任务描述                            │  │
│  │  检查维度: 代码质量/设计/完整性/安全/性能/可维护性/边界      │  │
│  │  产出: { verdict(PASS/FAIL), issues[{severity,file,line,    │  │
│  │          description,suggestion}], timestamp }              │  │
│  │  回退: verdict=FAIL → Worker 按 issues 逐条修复 → 再审查    │  │
│  └──────────────────────────┬──────────────────────────────┘     │
│                              │ 审查通过                            │
│  ┌─ 步骤C: Tester 测试 ←───有问题→Worker修复→再测试 (loop) ─┐  │
│  │  先行条件: 确认代码是最新版（git HEAD 验证）                  │  │
│  │  动作:                                                    │  │
│  │    1. 运行已有测试 → 全部通过？                              │  │
│  │    2. 补充测试（正常路径/异常路径/边界值/集成）               │  │
│  │    3. 新鲜运行所有测试 → 记录结果                            │  │
│  │  产出: { fresh_run:true, git_head, timestamp,              │  │
│  │          results{unit,integration,boundary},               │  │
│  │          coverage, new_tests_added[] }                     │  │
│  │  回退: 任何测试失败 → Worker 定位根因修复 → 旧结果作废 →    │  │
│  │        重新跑所有测试                                        │  │
│  └──────────────────────────┬──────────────────────────────┘     │
│                              │ 测试通过                            │
│  ┌─ 步骤D: Approval 拦截审视 ←──质疑→对应角色修正→再审视 (loop)┐ │
│  │  输入: Reviewer 报告 + Tester 报告                          │  │
│  │  检查:                                                  │  │
│  │    1. 审查结论可信度（检查维度是否全、依据是否具体）           │  │
│  │    2. 测试结论可信度（是否新鲜、断言≥2、mock合理）            │  │
│  │    3. 冰山追问（发现问题→追查同类问题）                       │  │
│  │    4. 反转假设（假设结论是错的→找反证）                       │  │
│  │  难度升级:                                              │  │
│  │    第1次❌ → L0正常走流程                                   │  │
│  │    第2次❌ → L1质疑"你确定走完流程了？"                      │  │
│  │    第3次❌ → L2深挖"底层逻辑是什么？"主动搜索验证            │  │
│  │    第4次❌ → L3全面审查（7项全面检查）                       │  │
│  │    第5次❌ → L4上报，Leader 重新评估换人/换方案              │  │
│  │  回退: 质疑→对应角色补充修正→再审视                        │  │
│  └──────────────────────────┬──────────────────────────────┘     │
│                              │ 批准                                │
│  ┌─ 还有下一批？────── 是 ──→ 回到分批 (loop)                    │
│  │ 全部完成                                                       │
│  ▼                                                                │
│ 进入第四阶段                                                       │
└──────────────────────────────────────────────────────────────────┘
```

### 并行分组规则

1. **无文件冲突**：比较任务涉及的"创建"和"修改"文件列表，无重叠的可以并行
2. **无前置依赖**：depends_on 为空或依赖的任务已在之前批次中完成
3. **同模块谨慎并行**：同一模块的任务建议串行，避免逻辑冲突
4. **文件锁是硬约束**：即使 Leader 判断无冲突，Worker 派发时仍需再次检查

### 回退条件汇总

| 环节 | 触发条件 | 回退动作 |
|------|---------|---------|
| Reviewer 审查 | verdict=FAIL | Worker 按 issues 逐条修复 → 再审查 |
| Tester 测试 | 任何测试失败 | Worker 定位根因修复 → 旧结果作废 → 全部重跑 |
| Approval 质疑 | 发现审查/测试遗漏 | 对应角色补充修正 → 再审视 |
| 难度升级 | 连续 2 次 Approval ❌ | 难度 +1 星，Leader 重新评估方案 |

## 第四阶段：总结报告

### 流程

```
所有任务完成后
  │
  ▼
Leader 汇总所有任务结果
  │ 产出: 总结报告
  │  - 任务概览（表格）
  │  - 问题记录（表格）
  │  - 技术方案（表格）
  │  - 知识图谱更新（表格）
  ▼
调度 DocKeeper 更新文档（按优先级）
  1. `.skeptics/docs/task.md`     → 标记每个任务的最终状态（解决/降级/未解决）
  2. `.skeptics/docs/progress.md`   → 更新进度百分比
  3. `.skeptics/docs/learned.md`    → 记录实施经验和验收问题
  4. `.skeptics/docs/requirement.md` → 标记需求状态为已完成
  ▼
调度 Memory Skill 更新知识图谱
  1. 从 `.skeptics/memory/JOURNAL.jsonl` 自动萃取新节点
  2. 更新现有节点权重
  3. 发现跨论关联
  4. 执行生命周期检查（冻结/归档）
  5. 更新 FACT.md 摘要
  ▼
向用户汇报总结报告
```
